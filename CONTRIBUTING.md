# Разработка и выпуск

## Перед изменением

1. Выполните `npm ci` на Node.js 22+.
2. Прочитайте `docs/REVIEW_HARDENING.md`, свежие changelog и относящийся к механике код.
3. Запускайте игру по HTTP, а не через file://. Для ручного теста чистого запуска используйте отдельный профиль браузера, не удаляя рабочие сохранения.
4. Не меняйте Firebase production-конфигурацию и правила доступа как побочный эффект UI-правки.

## Тесты

- `npm test` — обязательный быстрый набор и проверка всех runtime-скриптов/маркеров.
- `npm run test:browser` — реальный Chromium; включает движение восьми машин, восстановление сохранения, импорт, безопасные сообщения, установка SW с отказом сети и загрузка офлайн.
- `npm run test:baseline` — все legacy-тесты; любые новые падения завершают проверку ошибкой.
- `npm run test:all` — тот же набор, но любое старое падение тоже даёт ненулевой код.

Baseline `test_harness/known-failures.json` получен из изолированного прогона исходного commit 6481224. Это технический долг, а не разрешение добавлять падения. Новую запись можно добавлять только с воспроизведением на исходном коде и объяснением. При исправлении теста удалите запись.

Новые тесты используйте с `createSandbox(data, {strictDOM:true, strictRules:true, elementIds:[...]})`, когда возможно. Для старых тестов существует явный `prelude`: `createSandbox(data, {prelude: source})`. Никакой файл из /tmp не должен неявно исполняться. Таймеры песочницы выполняются синхронно и не подавляют исключения; настоящий порядок событий проверяйте в браузере.

`extract.js` использует Acorn и отвергает неоднозначные объявления. Не добавляйте дубли глобальных функций. Предпочтительное направление — вынос чистой логики из index.html в модули и прямой импорт в тесты.

## Обработка данных и HTML

- Не превращайте ошибку миграции в сброс кампании.
- Проверяйте возвращаемое значение saveData() в операциях, успех которых зависит от записи.
- Устанавливайте импорт через installImportedData(), не подменяйте appData перед обычным saveData().
- Для текста используйте textContent; для вставок в HTML — escapeCardHtml. Для URL изображений используйте safeImageUrl плюс экранирование атрибута.
- safeLogHtml допускает только простое форматирование без атрибутов. Это не универсальный sanitizer для интерактивных панелей.
- Не вставляйте пользовательские значения в строковые inline onclick/onchange. Создавайте обработчик через addEventListener/замыкание.

## Выпуск

1. Обновите APP_VERSION и видимые номера в index.html, short_name в manifest.json, имя кэша и BUILD-маркер service-worker.js, BUILD-маркеры подключённых собственных JS-модулей.
2. Согласуйте version в package.json и package-lock.json. `js/firebase-offline.js` — сторонний vendored bundle, он не получает игровой BUILD-маркер.
3. Добавьте changelogs/CHANGELOG-v*.md; актуализируйте README и затронутую документацию.
4. Выполните npm test, npm run test:browser, npm run test:baseline и git diff --check.
5. Для новой исполняемой зависимости добавьте её в CORE_ASSETS. verify_build.py завершится ошибкой, если подключённый скрипт/стиль не обязателен в офлайн-кэше.
6. Проверьте обновление существующей PWA и сохранение кампании на реальном устройстве. Android/WebView и реальный двухпользовательский Firestore-матч остаются отдельными ручными проверками.

GitHub Actions запускает проверки для PR и main и сохраняет JSON-отчёт legacy-прогона. Развёртывание игры/правил Firebase этим workflow не выполняется.
